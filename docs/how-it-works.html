1What Peek is

  • An in-app inspector for iOS apps: a floating button that opens a panel.
  • It shows three things: network requests, socket messages, and analytics events.
  • It is for QA and developers testing on real devices, with no proxy, cable or debugger.
  • Swift Package, iOS 16.6+, no dependencies, MIT license.
  • Repo: github.com/mohammadhamdan1991/Peek

2The big picture

Every piece of data follows the same path:

Your appmakes a request, tracks an event
→
Capturea hook hands the raw data to Peek (~1 µs)
→
Background queueredact, check, convert
→
Record storebounded, in memory
→
UIbutton + panel, refreshed ≤ 4×/s
  • Nothing is written to disk. Data lives only while the app runs.
  • The app is never slowed down. The calling thread only enqueues; all work happens on a background queue.
  • The UI never blocks capture. It reads snapshots and is told when something changed.

3The two modules

PeekCore

  • Foundation only: no UIKit, no SwiftUI.
  • Capture, records, storage, redaction, checks, exports.
  • Runs on macOS too, so its tests run fast with swift test.

Peek

  • The UI: floating button, panel, lists, detail screens.
  • The public entry point: Inspector.
  • Depends on PeekCore and re-exports it.
Inspector.start()                    // show the button, start capturing
Inspector.capture                    // HTTP input
Inspector.socketCapture              // socket input
Inspector.eventCapture               // analytics input
Inspector.http / .sockets / .events  // the three stores

There are two kinds of input: automatic (Peek hooks the system or an SDK) and explicit (your code calls Peek).

Why swizzling is safe here: the original method is always called with the same arguments, so the app and the SDK behave exactly as before. If an SDK isn't linked, its hook is simply skipped.

5Life of one request

  1. Start. The app sends POST /login. The hook calls capture.started(id, url, headers, body).
  2. Hand-off. Peek reads the current redaction rules, then puts the work on its serial background queue and returns. The app continues.
  3. Build the record. On the queue, Peek makes an HTTPRecord with two copies: the redacted one and the original one.
  4. Store. The record goes into the HTTP store. Observers get a "something changed" tick.
  5. Response. The completion handler fires. capture.finished(id, status, headers, body, error) updates the same record by id.
  6. Timing. URLSession reports metrics (DNS, connect, TLS, waiting, download). capture.timing(id, …) adds the waterfall.
  7. Show. The open list refreshes (at most 4 times per second) and the new row appears.

Retries of one logical call share a correlationID, so the detail screen shows "attempt 2 of 3".

6Where records live

  • Each kind has its own RecordStore: HTTP, sockets, events.
  • Bounded by count and by bytes. HTTP: 1,000 records or 25 MB. Sockets: 2,000 or 10 MB. Events: 2,000 or 5 MB.
  • When full, the oldest records are dropped first.
  • Bodies larger than 1 MB are truncated, cut on a UTF-8 character boundary so text stays readable.
  • Thread safety: one small lock (OSAllocatedUnfairLock) around the array.
  • Change notifications: an AsyncStream per screen that coalesces. A slow screen sees one pending tick, never a backlog.
  • Stores start paused and only open after Inspector.start passes its checks.
  • Pause stops new requests but still completes the ones already in flight. Clear empties everything.

7Redaction

Two copies of everything

  • Every record keeps a redacted copy (shown by default) and the original values (in memory only).
  • The Redact secrets switch picks which copy the panel shows and exports.
  • Turning it off reveals everything already captured; turning it on hides it again.
  • The switch resets to "on" at every launch.

Copies go to the local pasteboard only (no Universal Clipboard) and expire after 10 minutes. Shared files are encrypted on disk and deleted when the share sheet closes.

8Analytics events and checks

  • An EventRecord holds: name, source type, kind, and one delivery per destination (name + typed properties).
  • Kinds: event, screen view, identity, log, error.
  • Dropped destinations (asked for, but the app has no tracker) are shown struck through.
  • Values are typed the way SDKs see them: string, int, double, bool, or "other" (arrays, dates…).

Checks (warnings never change the payload)

9The UI

Floating button

  • Lives in its own window above the app (one per scene), so it never touches your view hierarchy.
  • The window only claims touches on the button; everything else passes through to the app.
  • Drag to move, snaps to an edge, docks half-hidden when idle, drag onto ✕ to hide.
  • Badge shows new failures and warnings. Long-press for quick actions (copy last cURL, pause, clear).

Panel

  • A SwiftUI sheet (half or full height) with one tab per tool: Network and Events.
  • Screens read snapshots from the stores; filtering and search run in the model, never in the view body.
  • Search is debounced; body search starts at 3 characters.
  • Always dark, with its own colours, so it looks the same in any host app.
  • Accessibility: VoiceOver labels and actions, Dynamic Type, 44 pt targets, Reduce Motion.

10Staying out of production

Four layers, from strongest to backstop:

#LayerWhat it does
1PEEK_DISABLED flagEvery source file is wrapped in #if !PEEK_DISABLED. Set it on release builds and Peek compiles to nothing.
2Your own call siteCall Inspector.start only in debug/QA builds (e.g. inside #if DEBUG).
3Runtime gateInspector.start refuses when isProductionEnvironment is true, the bundle id isn't allowed, or it's an App Store install.
4Guard scriptScripts/verify_no_peek.sh scans the built app's binaries and fails CI if any Peek code is inside.
Trade-off: Peek compiles by default so any app can use it. A build that forgets PEEK_DISABLED would include it; layers 3 and 4 catch that, so run the guard on every release archive.

11Performance and memory

  • Cost on the calling thread: about 1 µs per event (an enqueue).
  • Redaction regexes are compiled once; key checks are cached per body.
  • Memory is capped by the store limits (about 40 MB worst case, counting both copies).
  • The UI refreshes at most 4 times per second, however busy the app is.
  • No retain cycles: hooks capture what they need, not self; screens hold weak references to tasks.

12How Yassir's apps use it

  • Driver adds Peek as a Swift package (Tuist). Production configurations define PEEK_DISABLED through an exhaustive switch, so a new environment must choose explicitly.
  • Rider compiles Peek's source folders as its own framework targets, because Xcode can't pass the flag into a regular package.
  • Network: YassirNetworking's logger feeds Inspector.capture (retries and decoding errors included).
  • Sockets: YassirSocket's event sink feeds Inspector.socketCapture.
  • Analytics: each app's analytics sink feeds Inspector.eventCapture; direct SDK calls (identity, Crashlytics, Datadog, Screeb…) are reported next to them.
  • The guard script runs on every Production build (Driver: Fastfile; Rider: a build phase).

13Tests and CI

  • 76 tests in PeekCore: stores, capture, redaction, exports (cURL, HAR), event checks, swizzled capture with fake SDK classes.
  • GitHub Actions on every push: tests on macOS, an iOS build, and a check that a PEEK_DISABLED build contains no Peek symbols.
  • The Example/ app sends real requests and sample events, for trying it by hand.
